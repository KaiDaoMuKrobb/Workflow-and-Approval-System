# ExpenseFlow — deployment

How to build, run, test and release ExpenseFlow, and how to find out which
commit is currently serving traffic. Someone who has never seen this repository
should be able to reproduce the deployment from this page alone.

No secret value appears in this file or anywhere else in the repository.

---

## 1. Stack

| Layer | What we use |
|---|---|
| Application | Next.js 14 (App Router), React 18, TypeScript 5.6 |
| Styling | Tailwind CSS 3.4 |
| Database | PostgreSQL 16 |
| ORM and migrations | Prisma 5.21 (`prisma migrate`, `prisma db seed`) |
| Authentication | JWT in an HttpOnly cookie, `bcryptjs` for password hashing |
| Tests | Vitest 2.1 (unit and API), Playwright 1.48 (end-to-end, not run in CI) |
| Container | `node:24-alpine`, multi-stage, Next.js `output: 'standalone'` |
| Local orchestration | Docker Compose (postgres, migrate, app) |
| Cloud | Cloud Run (service and job), Cloud SQL for PostgreSQL, Artifact Registry, Secret Manager, Cloud Build |
| CI/CD | GitHub Actions, keyless authentication through Workload Identity Federation |

### What differs from the reference stack

The Lab 5 starter kit assumes a repository with a separate client and server.
ExpenseFlow is a single Next.js application at the repository root, so:

- `.github/workflows/ci-docker.yml` builds and tests one project instead of two,
  and also runs the offline checks for `deploy/` (`bash -n`, the two stub tests
  and `test_smoke.py`).
- `.github/workflows/deploy.yml` is the kit's file with four changes: the Cloud
  Run service name, the migration job name, the Artifact Registry image path and
  the wording of the deployment summary. The environment name `demo`, the job id
  `test-and-docker` and the four WIF variables are unchanged.
- `deploy/smoke_test.py` checks `/api/health`, `/api/ready`, `/` and `/login`.
  The kit's example checked `/api/categories`, which this application does not
  have.
- The image runs `node server.js` from the standalone output. The standalone
  build emits its own cut-down `package.json`, so the real one is copied in
  afterwards for the `prisma` block.

## 2. Environment variables

### Application

| Variable | Purpose | Secret | Where the value comes from |
|---|---|---|---|
| `DATABASE_URL` | PostgreSQL connection string | **Yes** | Local: `.env`, copied from `.env.example`. Cloud: Secret Manager `expenseflow-database-url`, injected by Cloud Run |
| `JWT_SECRET` | Signs and verifies the session cookie | **Yes** | Local: `.env`. Cloud: Secret Manager `expenseflow-jwt-secret`, generated by `deploy/deploy.sh` |
| `NODE_ENV` | `development` or `production` | No | `.env` locally, `--set-env-vars` on Cloud Run |
| `TZ` | Server time zone, `Asia/Bangkok` | No | Dockerfile default, also set on Cloud Run |
| `HOSTNAME` | Must be `0.0.0.0` so the standalone server listens outside the container | No | Dockerfile default, also set on Cloud Run |
| `PORT` | Listening port, `3000` | No | Dockerfile default |
| `COOKIE_SECURE` | Overrides the `Secure` flag on the session cookie; `false` for plain HTTP locally | No | `.env` locally. Not set in the cloud, where HTTPS makes the default correct |
| `SEED_DEMO_DATA` | `"true"` lets `prisma db seed` create the four demo accounts; anything else skips seeding | No | `.env` locally, set on the Cloud Run job by `deploy/deploy.sh --demo` |
| `DEMO_USER_PASSWORD` | Password hashed into the demo accounts at seed time; required when `SEED_DEMO_DATA=true` | **Yes** | Local: `.env`. Cloud: Secret Manager `expenseflow-demo-password`, generated by `deploy/deploy.sh --demo` |

### Docker Compose only

| Variable | Purpose | Secret | Default |
|---|---|---|---|
| `POSTGRES_USER` | Database user for the local container | No | `postgres` |
| `POSTGRES_PASSWORD` | Its password; local container only, never reachable from outside the machine | No | `postgres` |
| `POSTGRES_DB` | Database name | No | `expenseflow` |

### GitHub environment `demo`

These are variables, not secrets. None of them is sensitive: they identify the
project and the identity to assume.

| Variable | Value |
|---|---|
| `GCP_PROJECT_ID` | `cpe334-sec31-expenseflow` |
| `GCP_REGION` | `asia-southeast1` |
| `WIF_PROVIDER` | the Workload Identity provider resource path |
| `WIF_SERVICE_ACCOUNT` | `github-deployer@cpe334-sec31-expenseflow.iam.gserviceaccount.com` |

The environment has **no secrets**. The optional authenticated smoke check
(`SMOKE_EMAIL` as a variable plus `SMOKE_PASSWORD` as a secret) is deliberately
not configured, so `deploy/smoke_test.py` prints `SKIP login` and no credential
is stored in GitHub.

### Why no secret is committed

- `.env` is listed in `.gitignore` and `git ls-files .env` returns nothing.
- `.env.example` holds placeholders only, for example
  `JWT_SECRET="replace-with-a-secure-secret-in-production"`.
- Every real value lives in Secret Manager and is injected at runtime with
  `--set-secrets`. `deploy/deploy.sh` prints the secret **names**, never the
  values.
- No service-account JSON key exists anywhere. GitHub Actions authenticates to
  Google Cloud with Workload Identity Federation.

## 3. Commands

### Run locally with Docker Compose

```bash
cp .env.example .env
docker compose up -d
docker compose ps
```

No editing of `.env` is required. `docker compose ps` should show postgres
healthy, migrate exited with 0, and app running. The application is then on
<http://localhost:3000>.

Data lives in the named volume `postgres_data`, so `docker compose down`
followed by `docker compose up -d` keeps every record. `docker compose down -v`
deletes the volume and the data with it.

### Run locally without Docker

```bash
npm ci
npx prisma migrate deploy
npm run db:seed
npm run dev
```

### Build, test, migrate, seed

| Task | Command |
|---|---|
| Install | `npm ci` |
| Typecheck | `npx tsc --noEmit` |
| Unit and API tests | `npm test` (Vitest: 11 files, 66 tests) |
| End-to-end tests | `npm run test:e2e` (Playwright; not run in CI) |
| Build | `npm run build` (runs `prisma generate` first) |
| Apply migrations | `npx prisma migrate deploy` |
| Seed demo accounts | `npm run db:seed` (needs `SEED_DEMO_DATA=true` and `DEMO_USER_PASSWORD`) |
| Build the production image | `docker build -t expenseflow .` |

The API tests need a reachable PostgreSQL. Without one they are skipped, which
reads as failures in the summary, so start the database first.

### Offline checks for the deployment scripts

These run in CI and touch nothing in Google Cloud:

```bash
bash -n deploy/deploy.sh deploy/teardown.sh deploy/release.sh
bash deploy/tests/test_deploy_stub.sh
bash deploy/tests/test_release_stub.sh
python3 -m unittest discover -s deploy/tests -p 'test_smoke.py'
```

| Runtime service account | `expenseflow-runner@…` — only `roles/cloudsql.client` |
| Deployer service account | `github-deployer@…` — Artifact Registry Writer, Cloud Build Editor, Cloud Run Developer |
| Secrets | `expenseflow-database-url`, `expenseflow-jwt-secret`, `expenseflow-demo-password` |

Secret access is granted per secret to the two service accounts, never
project-wide.

### First-time creation

`deploy/deploy.sh` is idempotent and creates everything above. It must be run by
a project **Owner**, because it sets project-level IAM bindings; Editor is not
enough.

```bash
gcloud config set project cpe334-sec31-expenseflow
DRY_RUN=1 bash deploy/deploy.sh --demo
bash deploy/deploy.sh --demo
```

The first run with `DRY_RUN=1` prints every gcloud command and executes none.
`--demo` seeds the four demo accounts and creates `expenseflow-demo-password`;
without it the database has no users.

## 5. Release procedure

Nobody types a deploy command. A merge into `main` deploys.

1. Branch from `staging`.
2. Open a pull request into `staging`. `test-and-docker` must be green, and the
   other teammate reviews it and merges.
3. Open the release pull request: base `main`, compare `staging`. The
   `protect-main` ruleset requires one approving review and a green
   `test-and-docker`, and the branch must be up to date with `main`.
4. Merging pushes to `main`, which starts **Deploy demo** by itself. It runs the
   CI workflow first, authenticates to Google Cloud without a key, builds and
   pushes the image tagged with the merge commit SHA, runs `deploy/release.sh`
   (resolve digest, run the migration job, update the service, move all traffic
   to the new revision), smoke-tests the public URL, and writes a deployment
   summary.

A full release takes about six minutes, because the image is built twice: once
in CI and once in the deploy job.

### Which commit is running

The quickest answer is the run summary: **Actions → Deploy demo → the latest
successful run → Summary**, and read `Commit image tag`. That is the full
40-character commit SHA.

From the command line:

```bash
gcloud run services describe expenseflow \
  --region asia-southeast1 --project cpe334-sec31-expenseflow \
  --format='value(spec.template.spec.containers[0].image)'

gcloud artifacts docker images list \
  asia-southeast1-docker.pkg.dev/cpe334-sec31-expenseflow/expenseflow/expenseflow \
  --include-tags --format='table(version,tags,createTime)'
```

The first command gives the digest the service is serving; the second maps
digests to commit tags.

**The two digests will not look the same, and that is correct.** `docker push`
stores a manifest index, and the commit SHA is the tag on that index. Cloud Run
resolves the index to the platform-specific image and records *that* digest on
the revision. Both belong to the same artifact: the index carries the commit
tag, which is what the Artifact Registry listing shows.

### Rollback and roll-forward

A rollback changes only the Cloud Run revision. **Cloud SQL is a separate
resource and is not rolled back**, which is why every migration has to be
additive.

1. **Actions → Deploy demo → Run workflow.**
2. `Use workflow from` must be `main`. The `demo` environment allows deployments
   from `main` only and refuses anything else.
3. Put the full 40-character commit SHA of a release whose image already exists
   into `image_tag`, then run it.

Tests, the image build and the migration are all skipped; only the service is
pointed back at the existing image, which takes well under a minute. The run
summary shows `Rollback: true`.

To roll forward, run it again with the later SHA, or leave `image_tag` empty to
test, build and deploy the current `main`.

## 6. Choices that differ from the recommended practices

The Lab 5 handout asks for any departure from its recommended practices to be
written down here with the reason. There are three.

**Sessions are a stateless JWT, not rows in the database.** The recommendation
is to keep sessions in the database rather than in the container. ExpenseFlow
signs a JWT with `JWT_SECRET` and stores it in an HttpOnly cookie named
`expense_session`, so there is no session store at all — nothing is kept in the
container either, and the only state the application has is in Cloud SQL. The
point of the recommendation, that a restart or a redeploy must not lose
anything, still holds: a new revision keeps every signed-in user signed in,
because the cookie is verified rather than looked up.

**There are no file uploads.** Nothing in the application writes a file at
runtime, so there is nothing that would need to move out of the container.

**Cloud SQL is not paused while grading is open.** The recommendation is to
pause the instance when it is idle, but the handout also requires the service to
stay reachable until grading has been announced as finished, and a paused
instance makes the public URL fail. The instance is the smallest tier with
storage auto-increase off and Cloud Run scales to zero, so the idle cost is
small, and `deploy/teardown.sh` removes everything once grading is over.

Everything else follows the recommended practices: an alerts-only budget created
before any resource, Cloud Run at minimum 0 and maximum 3 instances, the
reference stack, demo accounts seeded for both roles with their password kept in
Secret Manager and shared privately rather than printed or committed, runtime
secrets in Secret Manager, Workload Identity Federation instead of a JSON key
with least-privilege service accounts, images tagged with the full commit SHA
and deployed by digest, migrations run in a separate job before the service is
updated, a read-only smoke test after every deploy, and rollback by redeploying
an earlier tag. The repository is public, as R-12 requires.

## 7. Keeping the service alive

Do not pause the Cloud SQL instance and do not run `deploy/teardown.sh` until
grading has been announced as finished. `teardown.sh` deletes the Cloud Run
service and job, the Artifact Registry repository, the Cloud SQL instance, the
secrets and the service account.
